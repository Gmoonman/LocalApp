## Context

完整方案见 docs/dsh-plugin-suite.md。本次从真正服务现有请求的运行时管理开始，三个业务插件不拆成大量没有独立用途的小插件。

## Goals / Non-Goals

完整目标包含多人使用、应用平台、应用开发和可选文档扩展，以及配对客户端贡献。用户、应用和身份的原生连接分别处理；通过唯一 Server 承载，不将单一 OperatorPeer 的 Gateway 直接共享给多个用户。

## Decisions

服务只接收 Server 认证后的用户身份，不接受客户端自报身份授予权限。多人运行时管理不依赖应用数据库；账号和模型持久化通过适配接入，业务路由由所属插件注册。Harness 和原生连接实现归多人插件，开发对话使用同一上下文的多人服务，不在路由内部另建上下文。已有用户模式保留兼容目录映射，用户与开发者身份分别隔离。每个 key 的创建与关闭串行，容量包含正在创建的条目。配置变更先标记对应条目失效，晚完成的工厂结果必须关闭，不能重新加入。Cordis 停止插件时关闭全部条目，不新增监听端口。

## Risks / Trade-offs

原生 Gateway 的连接选择、RPC、WebSocket、文件和后台执行必须共同验证隔离。现有 URL 和 SDK 通过适配保留；旧会话映射到原用户、应用与身份并继续使用原生日志。旧数据、密钥和应用包的升级与恢复必须以真实发行包验证，不能只靠新建测试目录。

## Migration Plan

1. 发布并验证 0.4.0（已完成）。
2. 运行时插件与现有 Server 接入。
3. 多人使用插件迁移账号、供应商、环境，并接入完整 dsh 客户端。
4. 应用平台迁移托管、权限、数据和发布。
5. 应用开发迁移源码、会话、创建和本地同步。
6. 验证升级、回滚及唯一 npm 包。

## 轨迹跟踪

完整插件化必须接入 dsh 原生 Session 事件、分页与投影，并在客户端加载 dsh Trajectory 插件。工具执行、模型请求、推理、时序与历史恢复使用 dsh 记录，不用自建消息列表代替。原生接口在认证后的独立用户、应用与身份上下文中处理，HTTP 和 WebSocket 均须覆盖隔离测试。
